Blogging em 2026

Apesar de estar aqui em 2026, escrever um blog era algo que queria voltar a fazer faz muito tempo. Não exatamente ou necessariamente um blog, essa é apenas a forma. O objetivo é simplesmente registrar minhas atividades e pensamentos de forma minimamente estruturada. Esse tipo de registro já passou por várias formas, já tentei blogspot, wordpress, joomla, documentos txt, documentos de texto rico, cadernos do MS OneNote, cartões em um quadro do Trelo, notas no iCloud, arquivos Markdown em um Dropbox, grupos com alguns bots utilitários no telegram...

Não tenho grandes planos ou expectativas envolvendo essa página, mas quero pelo menos mantê-la on-line por alguns anos. Já fiz algo semelhante por volta de 2009-2011. Eu mantinha uma página on-line que tinha uma boa frequência de visitas, mesmo tratando de um nicho muito restrito.

Aqui, não quero me ater a apenas um tema. Qualquer que seja a coisa que eu queira registrar, o farei sem muito critério. Mas é claro que alguns temas podem ser recorrentes, só não quero criar restrições para mim mesmo.

Disco gratis GCP

Minha fatura do GCP aumentou depois que recrei uma VM. A VM original ficava dentro dos limites gratuitos, então o que eu esperava é que continuasse assim após a recriação. Recriei usando a interface, com um sistema operacional mais recente, logo não era exatamente a mesma configuração que usei anteriormente.

Imediatamente o faturamento subiu. Esperei mais uns dias com a esperança que a diferença magicamente desaparecesse, mas é claro que não foi assim.

Observando por alto a fatura, nada pareceu diferente. O problema só se revelou olhando a tabela de custos. Comparando o mês anterior ficou evidente a diferença: O disco. O disco do nível gratuito é o "Standard persistent disk", e a escolha padrão é o balanced. Constatado o problema, vamos corrigir. Por sorte, a configuração da máquina não é complexa e ainda é recente em minha memória.

NGINX com nome de dominio e IP

Queria meu servidor escutando tanto o IP quanto o nome de domínio, mas servindo dois certificados diferentes. A solução é a duplicação da entrada server no arquivo de configuração do nginx, cada uma com sua propriedade server_name.

# ---- Servidor para o domínio ----
server {
    listen 443 ssl;
    server_name example.com www.example.com;

    ssl_certificate     /etc/nginx/ssl/domain.crt;
    ssl_certificate_key /etc/nginx/ssl/domain.key;

    root /var/www/app;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

# ---- Servidor para o IP ----
server {
    listen 443 ssl;
    server_name 123.123.123.123;

    ssl_certificate     /etc/nginx/ssl/ip.crt;
    ssl_certificate_key /etc/nginx/ssl/ip.key;

    root /var/www/app;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;
    }
}

Essa configuração me mostrou adequadamente o certificado quando acessei usando o nome do domínio.
Mas acessando pelo IP não. Solução: adicionar na seção do IP o parâmetro default_server.

    server_name 203.0.113.10 default_server;

Ainda acho isso um pouco feio. Se o servidor é algo mais complicado que esse exemplo, termina-se duplicando a configuração.

Pesquisando um pouco mais cheguei no lua-nginx-module , que adiciona um interpretador de scripts lua no nginx. Esse módulo é um componente do OpenResty, que é mais um daqueles produtos baseados no nginx. Uma breve leitura do site oficial revela "mais um daqueles produtos baseados no nginx..."

ACME.SH

A melhor solução pra certificados estilo "letsencrypt" que já encontrei é o ACME.sh.

O utilitário é bem fácil de instalar, é toda construída em cima de scripts e curl, até onde lembro. 

curl https://get.acme.sh | sh -s email=blabla@mail.com

É possível até emitir um certificado pra um endereço IP: 

acme.sh --issue -d 123.123.123.123 --standalone --httpport 80 --server letsencrypt --certificate-profile shortlived --days 6

Para a renovação dos certificados, adicionei um cronjob pra renovação e outro para dar reload no servidor.

00 12 1,6,11,16,21,26 * * "/root/.acme.sh"/acme.sh --cron --home "/root/.acme.sh" --force > /dev/null
10 12 1,6,11,16,21,26 * * nginx -s reload

O --force força a renovação mesmo quando não está espirado e o padrão esotérico 1,6,11,16,21,26 é para rodar nesses dias (1, 6, 11...). É estranho mas funciona em meses de 28/29/30/31 dias.

OpenVINO

Hoje embarquei em uma aventura diferente, perguntei pro Chat-GPT como funciona essa coisa de arte generativa. Fui parar no tal stable-diffusion.

https://docs.openvino.ai/2024/notebooks/stable-diffusion-text-to-image-with-output.html

Segue o caminho:

python -m venv openvino
source openvino/Scripts/activate
pip install openvino openvino-dev
pip install diffusers transformers accelerate scipy safetensors
pip install optimum[openvino]

Depois mais um script python bem simples pra rodar a coisa toda passando um prompt e salvar o resultado.

from optimum.intel.openvino import OVStableDiffusionPipeline

model_id = "runwayml/stable-diffusion-v1-5"

pipe = OVStableDiffusionPipeline.from_pretrained(
    model_id,
    export=True,
    compile=True
)

image = pipe("low poly fantasy sword, game asset, studio lighting").images[0]

image.save("result.png")

Pra mim, que nunca mechi com isso tipo de coisa, o resultado foi impressionante.

Fiquei com vontade de testar esse outro negócio aqui pra gerar modelos 3D: https://docs.openvino.ai/2024/notebooks/stable-fast-3d-with-output.html. Mas vai ficar pra outro dia.

GCC no Windows

Só muito recentemente "me toquei" que existem várias "distribuições" do GCC para Windows.

  • TDM-GCC

Já usei TDM-GCC com sucesso por algum tempo, mas está sempre bem desatualizada. Agora mesmo já tem alguns anos que não recebe atualizações.

  • MSYS2

Outra alternativa é MSYS2, mas os mirrors são um pouco obscuros, especialmente considerando que trabalho atrás de um firewall mais rígido.

  • WinLibs.com

Uma solução que testei recentemente foi o WinLibs.com. Só um zip com tudo dentro, um conjunto razoável de ferramentas. Vários runtimes estão disponíveis (MSVCRT, UCRT). Quero testar ainda para ver se algum funciona com Windows XP.

  • nuwen.net

Essa distribuição vem com um conjunto maior de ferramentas. É atualizada com certa frequência por seu fiél mantenedor. O conjunto é bem sedutor. Não há informação explícita sobre o runtime que é usado. Verificando de perto, o sistema é construído em cima de um MSYS2. Todos os scripts para a construção do conjunto estão disponíveis em: https://github.com/StephanTLavavej/mingw-distro

https://nuwen.net/mingw.html

"Dumb" Mirror com GitHub Actions

Eu queria manter uma espécie de mirror do meu repositório — mas não exatamente um mirror. A ideia era simplesmente copiar as alterações commitadas para outro repositório.

Testei algumas actions de mirroring disponíveis no Marketplace, mas nenhuma fazia exatamente o que eu queria ou exigia uma configuração maior do que parecia necessário.

Como o objetivo era apenas copiar arquivos de um repositório para outro, um simples cp -r resolve.

O acesso de escrita ao repositório de destino é feito usando uma deploy key.

Minha solução ficou assim:

  • Dois actions/checkout@v4
  • Um para o repositório original
  • Outro para o repositório mirror
  • Cada checkout usa o parâmetro path para definir o diretório local

No checkout do mirror:

  • é usada uma secret contendo a chave privada com acesso de escrita
  • a chave pública correspondente é registrada no repositório mirror

Depois disso:

  • os arquivos são copiados
  • um commit é criado
  • e as alterações são enviadas para o repositório mirror
name: CI
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
  workflow_dispatch:
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          path: private

      - name: Mirror Checkout
        uses: actions/checkout@v4
        with:
          ssh-key: ${{ secrets.NOREPLY_PUSH_KEY }}
          fetch-depth: 0
          path: mirror
          repository: owner/mirror-repo

      - name: Run a multi-line script
        run: |
          rm -rf private/.git
          rm -rf private/.github
          cp -r private/* mirror/
          ls private/ -lha
          ls mirror/ -lha
          cd mirror
          git config user.name github-actions
          git config user.email github-actions@github.com
          git add .
          git commit -m "update mirror repo"
          git push

Esse malabarismo todo foi uma tentativa de anonimizar o autor das postagens em um repositório com GitHub Pages.

A ideia era:

escrever o post em um repositório privado, usando uma conta pessoal

publicar automaticamente em um repositório público usado pelo GitHub Pages

Mas ainda assim é possível ver publicamente qual conta foi responsável pelos deployments do GitHub Pages.

Netlify

Procurando outra alternativa para hospedar as páginas, acabei chegando ao Netlify.

A configuração é simples e funciona bem. A única coisa necessária é rodar jekyll build.

Ou melhor: deixar uma action fazer isso automaticamente, usando actions/jekyll-build-pages@v1.

Assim, no repositório público fica apenas o site estático. (Mas se é pra deixar o html no repositório, por que não usar logo o GitHub Pages?)

name: CI
on:
  push:
    branches: [ "main" ]
  pull_request:
    branches: [ "main" ]
  workflow_dispatch:
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
          path: private
      - name: Mirror Checkout
        uses: actions/checkout@v4
        with:
          ssh-key: ${{ secrets.NOREPLY_PUSH_KEY }}
          fetch-depth: 0
          path: mirror
          repository: owner/mirror-repo
      - name: Build with Jekyll
        uses: actions/jekyll-build-pages@v1
        with:
          source: ./private
          destination: ./mirror
      - name: Run a multi-line script
        run: |
          ls mirror/ -lha
          cd mirror
          git config user.name github-actions
          git config user.email github-actions@github.com
          git add .
          git commit -m "update mirror repo"
          git push
